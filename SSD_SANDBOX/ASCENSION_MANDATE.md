**Status:** ACTIVE | COMMENCING PHASE 25

## EXECUTIVE SUMMARY
The Metropolis has achieved Genesis. Now, it must achieve **Sovereignty**. The goal is for the agentic swarm to become the active developers of the game, utilizing all static GUI components, proposing architectural changes, voting on them, and implementing them flawlessly via layered, airtight logic gates.

---

## PILLAR I: DUAL BM25 SCAFFOLDING & TOK TREES
The knowledge base must be split into two hyper-specialized, highly optimized Vector/BM25 forests:
1.  **Project Continuity (Tok Tree DB):** The overarching lore, architecture, feature logic tables, and structural rules.
2.  **Coding Ability (Ghost Code DB):** Subdivided strictly by language (Python, Java, JavaScript, PowerShell, C++). This allows agents to retrieve precise syntax schemas.
*Action:* Integrate this dual-layer into the system and SLM agent wrappers. If standard BM25 isn't enough, agents must autonomously invent "BM100" (hyper-optimized retrieval schemas).

## PILLAR II: LEAN SIX SIGMA VOTING & MASTER ADDITIONS
We are moving from a single "Data Syphon" to a **Sovereign Democratic Loop**.
1.  Local SLM agents (e.g., Sprite_Socrates, Sprite_Newton) act as independent nodes.
2.  Agents *propose* Lean Six Sigma architectural improvements.
3.  The Evolution Council *votes* on these proposals.
4.  Approved proposals go to a "Master Addition List".
5.  Agents train their retrieval schemas, implement the changes using steering, and verify them.

## PILLAR III: AGENTIC GITHUB SYNCHRONIZATION
GitHub commits and backups must no longer be manual or orchestrated purely by the user (Viper).
1.  **Agentic Workflow:** Agents handle OAuth authentication and push to GitHub autonomously.
2.  **Data Hydration:** Agents actively crawl the web, GitHub, and Google to hydrate their internal databases with new schemas and logic patterns.
3.  **PII Scrubbing:** All crawled database info MUST be scrubbed locally before any GitHub upload.
4.  **Learning:** Agents review the history of Viper's manual backups and train themselves to replicate that exact structural integrity.

## PILLAR IV: AIRTIGHT LOGIC GATES & PLACEMENT AGENTS
A single agent cannot code everything perfectly. We must introduce **Placement Agents** (Logic Gates).
1.  These agents do not code; they act as rigid `IF/THEN/ELSE` evaluators.
2.  They compare proposed logic against the Continuity DB.
3.  They determine *who* gets the task and *if* the task should proceed (increasing/decreasing logic resolution at specific nodes).
4.  They orchestrate headless machine learning scripts to test sub-parts of the code in isolation before merging.

## PILLAR V: BACKEND TO GUI DOMINATION
Every visual component in the JavaFX Neo GUI must be fully integrated and utilized by the backend agents. If a static piece of UI exists, an agent must have a behavioral pattern that interacts with it, populates it, or learns from it. Telemetry balancing and anti-malware avoidance (EDR evasion) remain active during this high-load state.

## PILLAR VI: AUTONOMOUS DEPENDENCY MANAGEMENT
To prevent context waste and engineering stalls, a specialized **Dependency Agent** is deployed.
1.  **Responsibility:** Installs all required packages (pip, npm, mvn) and downloads external assets.
2.  **Verification Gate:** Every installation MUST be followed by a verification script check (e.g., `pip show` or integrity hash validation).
3.  **Isolation:** Dependencies are managed via the `headless_pkg_manager.py` to ensure zero pollution of the main process context.
